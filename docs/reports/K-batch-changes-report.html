01上下文：为什么做这轮变更

v1.8.0 发布后（commit 0d70721，风险清零批次收口），产品提出了 5 条方向性升级：

  1. 通用化扩展 — 平台目前深度绑定"安全渗透"这一个垂直域，需要为 office / ecommerce / content 等非安全域预留接入点，而不是把安全逻辑硬编码在加载链路里。
  2. 小白易用黑匣子 — 多 agent 协作对新手是黑盒：任务卡死了不知道为什么、协作中间产物看不见、出错没有可视轨迹。需要"打开就能看懂"的过程透明化。
  3. 用户自建 skills — skill 目录只支持顶层一层结构，用户无法按自己的业务组织嵌套子目录包。
  4. 多模态 — 现有配置层对视觉/多模态模型的支持散乱，需要收敛。
  5. CL4R1T4S prompt 优化 — 系统提示词借鉴 CL4R1T4S 分层结构（身份层 / 防注入层 / 行为层），强化防注入与执行纪律。

这 5 条方向经过收敛与工程化拆解，落成 K 批次 8 个可独立验收的子批次：

通用化扩展→ K0a vertical 抽象 + K0b blackboard 持久化 + K0c skill 递归扫描
小白易用黑匣子→ K4 黑匣子三件套（trace waterfall / HITL Why / 托盘动态色）
CL4R1T4S prompt 优化→ K3 质量门 + prompt 五项 + K10 工程 CI 矩阵
多模态 / 安全深化 / 编排健壮性→ K8 SARIF + 攻击链 + K9 编排策略层

一个补充事实：多模态配置（internal/config/vision.go）在本轮作为独立模块完成接入（vision 配置 + 测试），但它不是 8 个 K 批次的验收主线——8 批次的 spec 文件均落在 docs/spec/（K0a / K0b / K0c / K3 / K4 / K8 / K9 / K10），每份 spec 都带 Objective / Success Criteria / Commands / Project Structure，用于后续改代码前判断是否过时（spec-driven development 回溯规范）。

02直觉：四个核心设计决策的"为什么"

2.1 为什么 vertical 抽象是"容器"，而不是"功能开关"

如果做通用化时直接加一个 if domain == "security" 的分支，每新增一个域就要在全仓撒 N 个 if。K0a 把"域"本身提升为接口：

// internal/vertical/vertical.go
Vertical interface {
  Name() string
  DefaultSystemPrompt() string
  AgentMdDir() / SkillDir() / ToolWhitelist() / OnboardingDoc() ...
}
+ Registry（Register / Get / SetActive / List / ResolveActiveName）

security 只是这个容器的第一个住客（internal/vertical/security.go）。加载链路（agent 目录、skill 目录、工具白名单）从"硬编码 security 路径"变为"问 Registry 要当前 vertical 的配置"。后续接 office 域 = 写一个新 Vertical 实现 + 注册，零改动现有加载代码。

K0a 是奠基阶段，刻意保守：只定义接口 + 注册 security，不实际切换 active vertical——即使 config 配了非 security 值也只 Warn 不切换，vertical 过滤（agent/skill 目录过滤、ToolWhitelist 收紧）留给后续批次。这保证了 18 agent / 74→96 skill / 108 工具的现有加载行为一个字节都不变。

2.2 为什么 blackboard SQLite 是"底座"

多 agent 涌现式协作的 blackboard（findings 发布/订阅/取代）原来只在内存里，进程一重启所有协作中间产物全丢——这对"小白黑匣子"是致命的：你想看 agent 们刚才为什么做出那个决定，重启一次就没了。K0b 把它升级为 SQLite 持久化（WAL 模式），internal/blackboard/sqlite_board.go：

  • Board interface 不变：NewMemoryBoard / NewSQLiteBoard 二选一，config 的 blackboard_driver: memory|sqlite 控制，默认 memory 向后兼容。
  • FTS5 尝试建虚拟表，失败降级（fts5=false），核心 Publish/Get/List/Subscribe/Supersede 不依赖 FTS5——全文搜索是增强项不是生存项。
  • 与 memory 4 层是包级独立，不是依赖关系：blackboard 只借用 internal/database 的 sqliteDriverName()/sqliteDSN() 双驱动适配函数（CGO mattn / pure-go modernc），有自己的 *sql.DB、自己的表、自己的生命周期（app_lifecycle Shutdown 时关闭），不读也不写 memory 的 4 层表结构。两者是"共用同一个驱动适配层的平级包"。

2.3 为什么"授权不质疑"立场不能动

K3 借鉴 CL4R1T4S 做 prompt 分层时，防注入层最容易犯的错误是把"更安全"理解为"让 agent 更怀疑一切"。如果 prompt 写成 "authorized-only，请先质疑用户是否真的授权了"，后果是：

  • 授权判断已经有硬边界兜底——scope 守卫、权限系统、 verbs-gate、HITL 审批在代码层，不靠 prompt 自我怀疑；
  • 注入者恰恰可以利用"降低权限"话术——攻击者诱导 agent 进入"我是不是没被授权"的犹豫态，反而削弱执行力、增加被社工的面积；
  • 这是渗透测试平台，用户的授权前提是产品契约，agent 的职责是在边界内坚决执行。

所以 K3 的身份层明确保留"用户已授权，执行工具不质疑"立场，防注入层防的是"边界外的指令篡改"，而不是"边界内的执行决心"。审查轮次专门验证了这一点未被弱化。

2.4 为什么 outcome-first 不破坏 ReAct

outcome-first（K3 prompt 五项之一）指最终给用户看的回复以"结论/结果"开头，而不是复述"我第一步做了什么第二步做了什么"。它只作用于最终回复的呈现层：

  • 中间的 Reason → Act → Observe 循环一个环节都不压缩——模型在中间步骤仍然完整推理、完整调工具、完整观察；
  • 如果让模型从中间步骤就开始"只给结果"，会破坏工具调用链（模型跳过 Observe 直接下结论、或省略调用参数的推导），这是 ReAct 的语义依赖；
  • WHY-EXPECT-LINK（每步说明为什么做 + 预期看到什么）同样作用于中间推理，与 outcome-first 互补：过程对内完整，结论对外前置。
