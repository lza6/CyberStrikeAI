1. 上下文与直觉：为什么有 J4/J5

CyberStrikeAI 是 AI 渗透测试平台：LLM 代理自主调用 100+ 安全工具（nmap、sqlmap、exec…）。这里的根本张力是——模型越自主，越需要确定性（非 LLM）的护栏。LLM 可能被注入、可能误解授权范围、可能把目标写到授权之外。所以项目在 LLM 推理之前叠了一层纯函数安全闸（ADR-0006）。

本轮的两个任务：

  • J4 · project scope 授权硬闸：项目（project）上配置的 scope_json（如 {"targets":["192.168.1.0/24"]}）原本只是拼进系统提示词的"软约定"——LLM 看得见但可以违反。本轮把它变成执行前强制校验：越界目标直接拒绝执行。
  • J5 · Capability Provider 生命周期：破坏性操作（修改/创建文件）走 plan → validate → execute → rollback → collect_artifacts 完整生命周期，执行前自动备份、失败自动回滚。

3. 架构直觉：两条执行链路

理解本设计的关键是：工具执行有两条平行链路，任何安全闸必须两条都覆盖。

链路 A · MCP 工具（nmap、sqlmap 等 yaml 工具）
handler → ExecuteMCPToolForConversation（注入 projectID）→ executor.ExecuteTool（yaml scope + project scope 硬闸在此）

链路 B · Eino 内置工具（execute、write_file、edit_file——由 Eino ADK filesystem 中间件直接挂载，不经 executor）
runner（传 ProjectID）→ runEinoADKAgentLoop（注入 ctx）→ scopeGuard.CheckExecute / capGuard.CheckFilesystemTool

初版的 J4 只覆盖了链路 A。链路 B 的 guard 虽然被构造了，但它从 ctx 读 projectID，而 ctx 里根本没有——这就是伪闭环 4 的根源。"组件存在"≠"组件生效"，数据流才是真相。
