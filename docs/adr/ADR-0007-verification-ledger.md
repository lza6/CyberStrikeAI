# ADR-0007: 验证台账（防重复测验的记忆点机制）

- 状态：Accepted
- 日期：2026-09-02
- 关联：ADR-0006（确定性安全层）、`docs/sop/safety-gate-capability-sop.md`

## 背景与问题

多次会话对同一代码区域重复跑同一批验证（sqlite 慢查询、i18n 对齐、go vet/test 全量等），每次都从头排查，浪费大量时间；且改过某区域后，旧验证结论可能过时，但没有机制提示"这块改过，需复验"。

## 决策

采用**分层验证台账**，每层各司其职：

1. **`workflow_status.md` 验证日志**（已存在）：记录每次批次的验证命令、结果、披露边界。按时间倒序追加。**AI 会话开始时优先读最近 2-3 条日志**，确认目标区域是否已被验证过、是否已被后续改动。
2. **`docs/sop/` SOP 文件**（新增）：把可复用的实施流程 + 已知坑清单沉淀为 SOP（首个：`safety-gate-capability-sop.md`）。改对应领域前先读第 4 节"已知坑清单"。
3. **ADR**：只记架构决策与理由，不记验证过程。

## 判定规则（AI 执行时遵循）

- 验证记录的**范围标注**：每条验证日志必须写明"覆盖的包/文件/命令"，让后续会话能精确判断命中。
- **过时判定**：若目标文件在最近一条覆盖它的验证日志之后又被改动（git log 或 workflow_status 可查），旧结论视为过时，需对该区域定向复验（不必全量重跑）。
- **未改动区域**：优先信任台账结论，不重复跑同一验证。需要补充证据时做定向验证而非全量。

## 后果

- 正面：消除重复测验浪费；改动后自动触发"该区域需复验"意识；验证结论可追溯。
- 负面：台账本身需要维护纪律（每批次必须追加日志）；台账过大后需归档（超 500 行时把旧批次移入 `docs/archive/`）。
